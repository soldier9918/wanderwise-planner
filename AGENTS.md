# Agent rules

- AI calls live in edge functions (`generate-script` for scripts, `scene-asset` for per-scene image/voiceover); the browser never holds the AI key. Why: keeps credentials server-side.
- Scenes are rows in `video_scenes` (not JSON on `videos`) so per-scene assets can be generated in parallel without overwrite races.
- Generated media is stored in the private `video-assets` bucket under `<user_id>/<video_id>/` and shown via signed URLs. Why: users only see their own files.
- Exports render in-browser; `video-export` authorises: server hash, free (no credits, no watermark), signed upload to `exports/`, identical versions re-download free. Why: untrusted client.
- "Use real facts" scripts search the web via the Firecrawl connector inside `generate-script` and store cited URLs in `videos.sources`. Why: grounds real-event scripts in sources users can check.
- Background music is composed in the browser (Web Audio) per mood, with uploads stored in `video-assets`; ducking is a per-video toggle. Why: no licensing risk and no AI credits.
- Per-scene "Animate scene" uses image-to-video via the `animate-scene` edge function (start job, client polls status, MP4 saved to `video-assets`, path in `video_scenes.clip_path`). Why: video jobs take minutes and gateway URLs expire.
- One-time top-ups charge through `create-checkout` (Stripe payment mode) and credit the ledger from the webhook at 25 credits per £1; auto top-up preferences stay device-local drafts only and are never billing authorization. Why: only real, verified payments may add credits.
- Free accounts get +30 monthly: daily cron `grant_monthly_free_credits_all` plus `claim_monthly_free_credits` on load; one grant per month, subscribers/admins skipped. Why: works without login.
- Credits live in `credit_ledger` (append-only, written only by DB functions/triggers or server code; users read-only). Balance = sum of rows. Starter credits come from a signup trigger; referrals via the `claim_referral` RPC. Every paid AI action is charged up front in its edge function via `_shared/credits.ts` (`spend_credits` RPC, service-role only, admins free) and refunded on failure; costs must match `src/lib/credits.ts`. Why: clients can't mint credits.
- "Article to video" (`/from-url`) reuses the Dashboard form; `generate-script` scrapes the link via Firecrawl and stores it in `videos.source_url`/`sources`. Why: one script pipeline for ideas and links.
- Stock B-roll comes from Pixabay (search results cached 15 min to respect rate limits) via the `stock-broll` edge function, saved as the scene's `clip_path` with `clip_credit` set; credit estimates count only clips without `clip_credit` as AI animations. Why: stock footage is free, AI animation is not.
- Narration speed is applied at playback (preview + export, pitch preserved); accent is a TTS instruction in `scene-asset`. Why: speed changes need no re-recording.
- "Remix for Shorts" copies a video and its scene rows into a new 9:16 video that reuses the same media paths (no regeneration). Why: original stays intact and remixing costs no credits; never delete shared media when a video row is deleted.
- My Library (/library) stores user files privately in video-assets under <user_id>/library/, listed via storage (no table). Why: reuses owner-scoped storage policies.
- Admin access uses the `user_roles` table + `has_role()`; admin data comes only from SECURITY DEFINER `admin_*` RPCs that check the role. Admins skip the export watermark. Why: never trust client-side checks for privileges.
- Tiers (`planTierOf`): Free/Creator/Pro length and 1080p caps enforced in generate-script, video-export and DB trigger; tier = active `user_subscriptions` plan_tier, admin = Pro; top-ups never unlock. Why: drives upgrades, server is the source of truth.
- Stripe (own account; Live only when STRIPE_MODE=live, all four Live settings validate (`_shared/stripeConfig.ts`) and DB `billing_config.live` agrees, else billing returns 503; subscriptions/customers are keyed per `livemode` and `has_active_subscription` only counts the current mode) runs via `create-checkout`, `customer-portal` and the signature-verified `stripe-webhook`; only the webhook writes `user_subscriptions` and grants monthly credits on `invoice.paid`, deduped by unique `credit_ledger.stripe_invoice_id` plus `processed_stripe_events`. Price→plan map lives in `_shared/stripe.ts`; unknown prices are ignored. Why: clients can't mint credits and other apps on the same Stripe account are never affected.
- Coupon codes live in `coupon_codes` (service-role only, no user policies) and are redeemed once per account by the SECURITY DEFINER `redeem_coupon` RPC, which logs the use in `coupon_redemptions` and writes the ledger row; admins manage codes from the Coupons tab via `admin_coupons` / `admin_create_coupon` / `admin_set_coupon_active`. Why: codes can't be read, edited or double-redeemed from the client.
- Series generator (`/series`) plans episodes via the `generate-series` edge function (free), then creates each episode through the normal `generate-script` pipeline with a brief that carries the shared visual motif. Why: one script/credit pipeline.
- Intro/outro cards are saved per account in `user_brand_cards` (jsonb, owner-only RLS; localStorage is just a cache) and drawn by `exportVideo` before/after scenes. Why: settings follow the user across devices.

- Billing history is fetched live from Stripe by the `billing-history` edge function (invoices + paid top-up checkout receipts) using only the server-stored customer id, and each record carries `ledger_keys` so credit lines can be matched to the money actually paid. Why: invoices stay authoritative and users can't request another customer's records.
- Plan changes: Vydora-only portal config (`customer-portal`); upgrades immediate (grant new minus old), downgrades at period end. Why: one allowance per cycle.
- Scheduled plan changes are read live from Stripe by read-only `subscription-status`, never stored. Why: follows portal changes.
- Free accounts with 0 credits are read-only: DB `can_mutate_project` gates project/scene writes and uploads; edge functions call `requireMutable` first. Why: server enforces credit exhaustion.

- Refunds/disputes reverse credits proportionally via `_shared/refunds.ts`, idempotent per refund amount/dispute id, capped at current balance (shortfall logged, never negative); won disputes restore. Why: no free credits from clawed-back money without creating debt.
